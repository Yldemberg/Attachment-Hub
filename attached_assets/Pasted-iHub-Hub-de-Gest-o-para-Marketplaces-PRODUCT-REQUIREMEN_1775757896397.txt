1. Visão Geral do Produto
O iHub é um Web App (PWA) que centraliza a gestão de vendas em marketplaces, começando pelo Mercado Livre. O produto elimina a fragmentação de informações críticas que prejudica pequenos vendedores, entregando visibilidade total em uma interface rápida e esteticamente superior.

1.1 Problema Central
O painel do Mercado Livre apresenta dados de forma fragmentada, sem hierarquia visual clara e com baixa eficiência para tomada de decisão. Pequenos vendedores perdem tempo navegando entre telas, cometem erros de estoque e respondem perguntas com atraso.

1.2 Proposta de Valor
Usuário entende qualquer informação crítica em menos de 2 segundos. Essa é a regra de ouro do iHub.

Funcionalidades do MVP:
Autenticação de usuários via Supabase Auth
Conexão com múltiplas contas Mercado Livre via OAuth 2.0
Dashboard com métricas consolidadas
Gestão de produtos com estoque em destaque máximo
Gestão de pedidos com filtros avançados
Resposta a perguntas de clientes diretamente no iHub
Notificações em tempo real (in-app + push PWA)
Sistema de trial de 30 dias + assinatura Stripe
Sincronização de estoque compartilhado por SKU

1.3 Público-Alvo
Pequenos e médios vendedores do Mercado Livre que possuem múltiplas contas ou múltiplos anúncios e precisam de visibilidade centralizada sem custo elevado de ferramentas enterprise.

3.8 RLS (Row Level Security)
Habilitar RLS em todas as tabelas. Políticas obrigatórias:
profiles: usuário acessa apenas o próprio registro (id = auth.uid()).
accounts: usuário acessa apenas contas onde user_id = auth.uid().
products / orders / questions: acesso via JOIN com accounts (account_id IN SELECT id FROM accounts WHERE user_id = auth.uid()).
notifications: usuário acessa apenas onde user_id = auth.uid().
⚠️  A API Node.js usa DATABASE_URL com role service_role que bypassa RLS. Isso é intencional — o backend já faz a validação de JWT e ownership.

3.9 Triggers Obrigatórios
Trigger 1: handle_new_user — Após INSERT em auth.users, cria automaticamente um registro em profiles com trial_ends_at = NOW() + 30 days.
Trigger 2: update_updated_at — Trigger genérico em todas as tabelas para manter updated_at = NOW() a cada UPDATE.


4. Integração Mercado Livre — Endpoints Exatos
⚠️  CRÍTICO: Usar exatamente estes endpoints. Erros de URL são a causa mais comum de falha na integração.

4.1 OAuth 2.0 — Fluxo de Autorização
Passo 1 — Gerar URL de autorização:
https://auth.mercadolivre.com.br/authorization?response_type=code&client_id={ML_CLIENT_ID}&redirect_uri={ML_REDIRECT_URI}

Passo 2 — Trocar code por tokens:
POST https://api.mercadolibre.com/oauth/token
Content-Type: application/x-www-form-urlencoded
Body: grant_type=authorization_code&client_id={ML_CLIENT_ID}&client_secret={ML_CLIENT_SECRET}&code={CODE}&redirect_uri={ML_REDIRECT_URI}

Resposta do token (salvar todos os campos no accounts):
{ "access_token": "...", "token_type": "Bearer", "expires_in": 21600,
  "scope": "...", "user_id": 123456789, "refresh_token": "..." }

Passo 3 — Renovar access_token (executar quando token_expires_at < NOW() + 5min):
POST https://api.mercadolibre.com/oauth/token
Body: grant_type=refresh_token&client_id={ML_CLIENT_ID}&client_secret={ML_CLIENT_SECRET}&refresh_token={REFRESH_TOKEN}

⚠️  O access_token expira em 6 horas. Implementar middleware que checa expiração antes de cada chamada à API ML e faz refresh automático.

4.4 Webhook do Mercado Livre
O backend deve expor um endpoint público que receberá notificações em tempo real do ML:
POST /api/webhooks/mercadolivre

Payload que o ML envia:
{ "_id": "...", "resource": "/questions/123456789", "user_id": 123456789,
  "topic": "questions", "application_id": "...", "attempts": 1,
  "sent": "2025-01-01T00:00:00.000Z", "received": "2025-01-01T00:00:01.000Z" }

Tópicos a registrar e tratar:
questions — Nova pergunta ou resposta.
orders_v2 — Novo pedido ou atualização de status.
items — Mudança em anúncio (estoque, status).

Lógica do webhook handler:
1. Extrair resource e topic do body.
2. Buscar ml_user_id para saber qual account atualizar.
3. Fazer GET no recurso indicado usando o access_token da conta correspondente.
4. Atualizar o banco de dados (upsert).
5. Inserir notificação na tabela notifications.
6. Responder com HTTP 200 imediatamente (ML requer resposta em < 500ms).
⚠️  Processar a lógica de forma assíncrona após responder 200. Usar setImmediate() ou queue.

7. Regras de Negócio Críticas
RN1: Sincronização de Estoque por SKU (CRÍTICA)
O SKU é a chave lógica que une anúncios do mesmo produto. Ao atualizar estoque via PATCH /api/products/sku/:sku/stock:
1. Buscar TODOS os produtos com o mesmo SKU no banco (inclusive de contas diferentes).
2. Para cada produto, verificar is_full. Se is_full = true, PULAR e logar aviso.
3. Para cada produto elegível, chamar PUT /items/{ml_item_id} com o novo estoque.
4. Atualizar available_quantity no banco após confirmação do ML.
5. Retornar resultado com lista de sucessos e falhas.
⚠️  Produtos FULL (Fulfillment ML) têm estoque gerenciado pelo armazém da ML. NÃO tentar editar — a API retorna erro 400.

RN2: Refresh Automático de Token ML
Antes de qualquer chamada à API do ML, o middleware deve:
1. Checar se token_expires_at < NOW() + 5 minutos.
2. Se sim, executar refresh usando o refresh_token.
3. Salvar novos access_token, refresh_token e token_expires_at no banco.
4. Prosseguir com a chamada original usando o novo token.
⚠️  O refresh_token também expira (em torno de 6 meses sem uso). Se o refresh falhar, marcar a conta como is_active = false e notificar o usuário.

RN3: Rate Limiting da API ML
O ML limita chamadas por app e por usuário. Estratégias obrigatórias:
Usar endpoint de busca em batch: GET /items?ids=MLB1,MLB2 (até 20 itens por chamada).
Sincronização completa apenas quando disparada manualmente ou via webhook.
Cache no banco: dados sincronizados servem requisições do frontend sem chamar ML.
Se API ML retornar 429, aguardar com exponential backoff (1s, 2s, 4s, max 30s).

RN4: Trial e Bloqueio de Funcionalidades
Ao cadastrar, profile recebe trial_ends_at = NOW() + 30 days e plan = trial.
Após expiração do trial, bloquear no backend: verificar plano no requireAuth middleware.
Funcionalidades bloqueadas devem retornar HTTP 402 com mensagem clara.
No frontend, mostrar banner de upgrade quando plan = trial e trial_ends_at < 7 dias.

RN5: Multi-Contas
Um usuário pode conectar múltiplas contas ML. Todas as listagens (produtos, pedidos, perguntas) suportam filtro por account_id. Sem filtro, retornar dados consolidados de todas as contas do usuário.

9. Fluxos Críticos
9.1 Fluxo de Autenticação
1. Usuário acessa /login ou /register.
2. Frontend chama Supabase Auth (signInWithPassword ou signUp).
3. Supabase retorna session com access_token (JWT).
4. Frontend armazena session no localStorage via supabase-js.
5. Todas as requisições à API Express incluem header: Authorization: Bearer {access_token}.
6. Backend valida JWT em lib/auth.ts usando SUPABASE_JWT_SECRET.
7. Extrai user.id do payload e injeta no req.user.
8. Rotas protegidas usam requireAuth middleware.
⚠️  NÃO implementar /api/auth/login ou /api/auth/register. Auth é 100% via Supabase no cliente.

9.2 Fluxo de Conexão de Conta ML
1. Usuário clica em "Conectar conta" em /integrations.
2. Frontend chama GET /api/accounts/connect/url.
3. Backend gera state (UUID salvo no banco para validação CSRF), retorna URL de auth do ML.
4. Frontend redireciona usuário para a URL do ML.
5. Usuário autoriza no ML, que redireciona para ML_REDIRECT_URI com code e state.
6. Backend (GET /api/accounts/connect/callback) valida state, troca code por tokens.
7. Backend salva tokens em accounts, chama GET /users/me para salvar ml_user_id e ml_nickname.
8. Dispara sincronização inicial assíncrona.
9. Redireciona para /integrations?success=true.

9.3 Fluxo de Sincronização
POST /api/accounts/:id/sync dispara:
1. Buscar lista de IDs de itens: GET /users/{ml_user_id}/items/search (paginado).
2. Buscar detalhes em lote: GET /items?ids=MLB1,MLB2,...MLB20 (batches de 20).
3. Upsert em products (ON CONFLICT ml_item_id DO UPDATE).
4. Buscar pedidos recentes: GET /orders/search?seller={ml_user_id}&sort=date_desc.
5. Upsert em orders.
6. Buscar perguntas não respondidas: GET /questions/search?seller_id={ml_user_id}&status=unanswered.
7. Upsert em questions.
8. Atualizar accounts.last_sync_at.


10. Escalabilidade e Boas Práticas
10.1 Requisitos Não-Funcionais
Retry automático: Todas as chamadas à API ML devem ter no mínimo 3 tentativas com backoff.
Logs estruturados: Usar pino-http no Express. Logar method, url, status, responseTime em JSON.
Tratamento de erros: Middleware global de erro retornando { error: { code, message } }.
Multi-tenant: user_id em todas as queries — NUNCA retornar dados de outro usuário.
Timeouts: API ML tem timeout de 30s. Configurar axios/fetch com timeout explícito.
Graceful shutdown: Tratar SIGTERM para fechar conexões limpamente no Replit.

10.2 Estratégia de Migração (Replit → Produção)
Fase 1 — MVP no Replit: Tudo em um Repl com concurrently rodando frontend (Vite) + backend (Express). Webhook via URL pública do Repl.
Fase 2 — Separar backend: Migrar api-server para Railway ou Render. Frontend continua em Replit ou migra para Vercel.
Fase 3 — Produção: Vercel (frontend) + Railway/Render (backend) + Supabase (banco). Custom domain.

10.3 Melhorias Estratégicas (Pós-MVP)
S1: Sistema de alertas inteligentes — estoque baixo, perguntas pendentes há X horas.
S2: Relatórios exportáveis (CSV/Excel) de vendas e estoque.
S3: Sugestão automática de resposta para perguntas frequentes (IA).
S4: Integração Shopee — mesmo schema, novo provider na tabela accounts.
S5: Dashboard de precificação — comparação com concorrentes.
S6: Automações via Supabase Edge Functions (sem N8N neste momento).


11. Instruções Especiais para o Agente (Replit AI)

1. USE EXATAMENTE as URLs de endpoint da API ML listadas na seção 4. Não inventar URLs.
2. USE EXATAMENTE os nomes de variáveis de ambiente da seção 6. Não criar variantes.
3. NUNCA criar rotas /api/auth/login ou /api/auth/register. Auth é 100% Supabase.
